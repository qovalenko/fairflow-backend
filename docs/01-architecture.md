# Архитектура

## 1. Форма системы

Монорепо npm-workspaces. Каждый workspace — самостоятельный сервис на NestJS 11
поверх Fastify; общие контракты вынесены в `@fairflow/shared`.

```text
          HTTP :3000
клиент ─────────────────▶  gateway  ──gRPC──▶  auth       (5001)
   JWT                        │               control    (5002)
                              │               contact    (5003)
                              ├──────────────▶ company    (5004)
                              │               pipe       (5005)
                              │               orders     (5006)
                              │               product    (5007)
                              │               activity   (5008)
                              │               documents  (5010)
                              │               reports    (5011)
                              │               automation (5012)
                              │               search     (5013)
                              │               audit      (5014)
                              │               notification (5015)
                              │               billing    (5016)
                              └──────────────▶ chat       (5017)
```

### Инварианты

1. **Gateway — единственная публичная точка входа.** REST под `/api/...`;
   gateway транслирует запросы в gRPC-вызовы доменов. GraphQL из системы
   изъят — сейчас поверхность только REST.
2. **Домены не отдают бизнес-логику по HTTP.** У доменного сервиса по HTTP
   живут ровно четыре эксплуатационных маршрута — контракт `ops-http-contract`
   в `@fairflow/shared`:

   | Маршрут | Ответ |
   | --- | --- |
   | `GET /healthz` | `200 { status: "ok" }` |
   | `GET /readyz` | `200 { status: "ok" }` / `503 { status: "error", message }` |
   | `GET /status` | `200 OpsStatusBody` |
   | `GET /metrics` | `200`, Prometheus text |

   Добавлять REST-эндпоинты с бизнес-логикой в доменный сервис нельзя — такой
   маршрут обходит авторизацию gateway.
3. **Домены общаются между собой только по gRPC.** Прямых обращений к чужой
   базе нет: у каждого домена своё хранилище, чужие данные берутся вызовом.
4. **Сборка начинается с `@fairflow/shared`** — от него зависят все остальные
   workspace'ы (`npm run build:shared`).

## 2. Хранилища

Два разных движка, разделение по природе данных.

**PostgreSQL** (одна база `fairflow`, отдельные схемы, Prisma 7 с
`@prisma/adapter-pg`) — то, где нужны транзакции и ссылочная целостность:

| Схема | Что лежит |
| --- | --- |
| `auth` | пользователи, сессии, сервисные API-ключи |
| `control` | организации, проекты, участники, подразделения |
| `gateway` | служебные данные точки входа |
| `billing` | лицензии, счета, платежи |

Доменные таблицы намеренно не в `public`.

> Имена каталогов миграций должны быть уникальны в пределах базы: два
> `..._init` в разных схемах ломают применение второго.

**MongoDB** — всё остальное: домены, где схема подвижна и ведущий паттерн
«документ целиком». Это `contact`, `company`, `pipe`, `orders`, `product`,
`activity`, `platform`, а также `documents`, `reports`, `automation`,
`search`, `chat`, `notification` и `audit` — всего 14 сервисов.

Плюс инфраструктура: Redis (кэш, идемпотентность), RabbitMQ (события между
доменами), MinIO/S3 (файлы документов).

## 3. Модульная платформа

Функциональность нарезана на **модули**, и набор модулей — свойство проекта, а
не инстанса. Реестр модулей (`shared/src/module-registry.ts`) описывает для
каждого: идентификатор, заблокирован ли он, настройки и — главное —
`policyCapabilities`, то есть какие права он приносит с собой.

Следствия:

- каталог прав проекта **вычисляется** как объединение возможностей включённых
  модулей плюс системные предметы, а не хранится таблицей;
- включили модуль в проекте — его ключи появились в каталоге, выключили —
  исчезли;
- обращение к маршруту выключенного модуля отвергается с `403 MODULE_DISABLED`
  до всякой проверки ролей.

Модули: `deals`, `orders`, `contacts`, `companies`, `products`, `activities`,
`documents`, `reports`, `statistics`, `automation`, `search`, `chat`,
`notifications`, `profile`.

## 4. События

Домены обмениваются фактами через RabbitMQ (топология — `shared/src/bus-topology.ts`).

Дедупликация двухуровневая, и уровни не надо путать:

- **на стороне потребителя** консьюмер отбрасывает повтор по
  `idempotencyKey ?? messageId` из конверта события (`shared/src/events.ts`);
- **на стороне издателя** факты аудита и outbox дедуплицируются по
  `x-gw-call-id` — идентификатору одного gateway→домен вызова, который нельзя
  подменить с клиента (см. [02-grpc-model.md](02-grpc-model.md) §2).

Необработанные сообщения уезжают в DLQ (`shared/src/consumer-dlq.ts`).

## 5. Добавление нового домена

1. Завести workspace и описать контракт в `proto/fairflow/<domain>/v1/`.
2. Поднять gRPC-сервер, реализовать ops-контракт по HTTP, повесить валидацию
   сервисного ключа на входящие вызовы.
3. Описать домен в манифесте модуля — реестр gRPC-клиентов gateway
   **генерируется** из манифестов (`listGatewayGrpcClients`), руками его
   не правят.
4. Добавить BFF-контроллер в gateway, который собирает исходящую метадату через
   `GatewayOutboundMetadataService`.
5. Если домен приносит пользовательские права — описать `policyCapabilities`
   в реестре модулей.
