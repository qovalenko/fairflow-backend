# Доменная модель

Три концепта держат всю систему: **проект** как граница изоляции, **сделка**
как единственная сущность продажи и **тип продажи** как описание процесса
оформления.

## 1. Проект — единица изоляции

Любая CRM-запись принадлежит проекту. Проект несёт собственный набор
включённых модулей, ролей и данных; данные разных проектов не пересекаются.

Изоляция реализована **не как база-на-тенанта**, а как обязательное поле плюс
фильтр:

- реестр проектов живёт в домене `control` (PostgreSQL, схема `control`,
  модель `Project`);
- CRM-домены хранят документы в MongoDB в общих коллекциях, и каждый документ
  несёт поле верхнего уровня `projectId`; каждый запрос строится с фильтром
  `{ projectId, … }`;
- транспортный ключ — доверенная gRPC-метадата `x-project-id`.

### Защита границы

`projectId` берётся из метадаты, а не из тела запроса. Если тело содержит
`projectId`, отличный от `x-project-id`, запрос отклоняется с
`PERMISSION_DENIED` (`shared/src/grpc/inbound-metadata.ts`). Это
defense-in-depth: подменить границу изоляции через body нельзя.

### Жизненный цикл

Поле `status`: `active` → `archived` → `pending_deletion` → `purged`.
Архивация переводит проект в состояние только-для-чтения; `isArchived`
поддерживается в согласованности со `status` для обратной совместимости.

При физическом удалении `control` публикует событие `control.project.purged`,
и доменные purge-консьюмеры удаляют данные проекта в своих коллекциях.

### Модули проекта

`Project.modules` — список включённых модулей, `moduleConfigs`,
`modulePolicies` и `visibilityConfig` рядом. Отключение модуля **не удаляет
данные**: скрываются меню, поля и вкладки; при обратном включении всё на
месте.

### Одиночное владение

В этой линии продукта организация как отдельная сущность снята: владельцем
проекта всегда выступает система (`ownerId` = системный якорь), а прежний
`owner_type` (`PERSONAL` / `ORGANIZATION`) дропнут. Единица изоляции ровно
одна — проект.

## 2. Сделка и воронка (deal-centric)

**Лид, заявка и продажа — не отдельные сущности.** Это одна сделка на разных
стадиях настраиваемой воронки (Pipeline).

Практические следствия:

- в системе нет «модуля лидов» и нет конвертации лид → сделка;
- есть перемещение по стадиям (`deals.stage:move`) и отдельная операция
  **квалификации** — превращение лёгких контактных полей сделки в настоящий
  контакт;
- воронка настраивается per-project: стадии, причины проигрыша, источники.

Домен `pipe` хранит сделки, воронки, историю стадий, причины проигрыша и
источники.

## 3. Продажа и тип продажи (order-centric)

**Продажа (Order)** — процесс оформления, порождаемый из сделки. Её поля,
этапы, документы и финальное действие диктует **тип продажи (Order Type)**.

Ключевая деталь связи: тип продажи привязан к продукту, и **ссылка идёт от
продукта к типу**, а не наоборот. Продукт знает, по какому процессу его
продают.

Домен `orders` хранит заказы, типы продаж и их ревизии.

## 4. Владение записями

«Сирот» не бывает: каждая запись принадлежит пользователю **или**
подразделению. В коде владение выражено полями `ownerId` / `assigneeId` и
`departmentId` / `ownerDepartmentId` на доменных документах. На этом же
строится видимость записей — см. [03-access-model.md](03-access-model.md).

## 5. Карта доменов

| Домен | Хранилище | За что отвечает |
| --- | --- | --- |
| `auth` | PostgreSQL (`auth`) | пользователи, сессии, сервисные API-ключи |
| `control` | PostgreSQL (`control`) | проекты, участники, подразделения, роли, гранты |
| `billing` | PostgreSQL (`billing`) | лицензии, счета, платежи |
| `pipe` | MongoDB | сделки, воронки, стадии |
| `orders` | MongoDB | продажи, типы продаж |
| `contact` | MongoDB | контакты |
| `company` | MongoDB | компании |
| `product` | MongoDB | каталог продуктов |
| `activity` | MongoDB | задачи, встречи, звонки |
| `documents` | MongoDB + S3 | документы и шаблоны |
| `reports` | MongoDB | отчёты |
| `automation` | MongoDB | правила автоматизации, вебхуки |
| `search` | MongoDB | поиск по сущностям проекта |
| `chat` | MongoDB | беседы и сообщения |
| `notification` | MongoDB | уведомления, почта |
| `audit` | MongoDB | журнал действий |
